# Шум канваса и premultiplied alpha: разбор и предложение

Вопрос тимлида (8 ноября): у подменённого канваса `getImageData` и PNG из `toDataURL` расходятся в 18 байтах
(iPhone; на симуляторе 16), у неподменённого — в 0. Нужно установить механизм, предложить решение и оценить его
цену. Чинить будет мак-агент; здесь разбор и модель, на которой его можно повторить.

Метки: **[прочитано]** — исходники WebKit или документация Apple; **[замерено]** — в Chromium (Playwright);
**[смоделировано]** — модель канваса с формулами WebKit (`webkit_sim.mjs`); **[данные устройств]** — прогоны q2
на симуляторе и iPhone.

## Короткий ответ

- **У приложения тот же дефект.** 18 байт дал `fp_patch.js` (стенд замеров). Его `fpNoisePixels`, его копия для
  PNG и вывод зерна побайтно совпадают с `ios/shim/fingerprint.js` приложения. CI приложения PNG с `getImageData`
  не сравнивает, поэтому дефект не видит.
- **Механизм.** Перехваченный `getImageData` отдаёт шумлённые значения, которые никогда не лежали в
  премультиплицированном хранилище. PNG делается из копии, в которую их положили через `putImageData`, поэтому
  в нём «округлённые хранилищем» значения. Пробник видит только часть расхождения: он читает PNG обратно через
  тот же перехваченный `getImageData`, и повторный шум часть разницы «чинит».
- **Настоящий масштаб больше.** Страница, которая сама разбирает байты PNG, увидит около 100 расходящихся байт,
  а не 16–18. Страница, знающая документированную формулу Apple, найдёт около 95 значений, которые WebKit вернуть
  не может, в одном вызове `getImageData`, вообще без PNG [смоделировано + замерено в Chromium].
- **Предложение: шуметь покрытие (альфу), а не цвет.** Подробности ниже. На модели все проверки согласованности
  дают 0. Изменение — около 15 строк в `fpNoisePixels`, без лишней работы во время выполнения. Риск один: решение
  опирается на точные формулы vImage, поэтому в CI нужна проверка таблицы на симуляторе и на iPhone.

## Как WebKit хранит и читает канвас [прочитано]

- 2D-канвас хранится премультиплицированным. `getImageData` и `putImageData` переводят через
  `PixelBufferConversion.cpp`. На Cocoa это Accelerate (`vImageUnpremultiplyData_RGBA8888`,
  `vImagePremultiplyData_RGBA8888`) на всех ветках safari-7618…7625 и на main.
- Формулы — по `vImage/Alpha.h` и комментариям в main:
  - `premul(v,a) = ⌊(v·a + 127)/255⌋`;
  - `unpremul(p,a) = ⌊(min(p,a)·255 + ⌊a/2⌋)/a⌋`.
- `toDataURL` и `toBlob` кодируют премультиплицированную картинку через ImageIO. Его код закрыт, поэтому его
  округление — вывод, а не чтение. Но при выключенном шуме расхождение 0 байт [данные устройств]: путь через PNG
  обратно без потерь.

## Неподвижные точки [смоделировано, все значения]

Пусть `rt(v) = unpremul(premul(v,a),a)` — то, что даёт запись значения в канвас и чтение обратно. При альфе a
неподвижных точек `rt` ровно a+1. Примеры:

- при a=10 сохраняется лишь {0, 26, 51, …, 255};
- при a=127 — только чётные значения.

Нынешний шум меняет младший бит цвета: `v → v^1`. При a ≤ 127 значение `v^1` никогда не сохраняется — хранилище
его «перекруглит». Полная таблица — `fixed.mjs` (пишет `fixed_points.tsv`).

## Предложение (q) — `proposed.js`

```js
const fpPremul = (v, a) => ((v * a + 127) / 255) | 0;
const fpUnpremul = (p, a) => ((Math.min(p, a) * 255 + (a >> 1)) / a) | 0;
function fpNoisePixels(data, seed) {
  for (let i = 0; i < data.length; i += 4) {
    const a = data[i + 3];
    if (a === 0 || a === 255) continue;
    const h = fpMix(seed, 0, a >> 1);              // решают зерно и класс альфы, не место пикселя
    if (h % 5 !== 0) continue;
    const b = (a & 0xfe) | ((h >>> 16) & 1);
    if (b === a || b === 0 || b === 255) continue;
    for (let k = i; k < i + 3; k++) data[k] = fpUnpremul(fpPremul(data[k], b), b);   // цвет, как он хранится при альфе b
    data[i + 3] = b;
  }
  return data;
}
```

Свойства проверены перебором всех представимых пикселей при четырёх зёрнах (`test_proposed.mjs`). Отдельно,
своей хэш-функцией, повторено вне этой папки.

- Каждый выход — значение, которое `getImageData` может вернуть.
- Повторное применение ничего не меняет.
- Чёрный и белый не меняются.
- Отсюда: PNG равен `getImageData`, нарисованное обратно читается так же, put/get ничего не меняет.
- Шум зависит от содержимого, а не от места пикселя, поэтому подпрямоугольник и копия со сдвигом сходятся.

Чего не исправляет ни один вариант:

- **Известные полупрозрачные пиксели.** Страница рисует `fillRect` с альфой k/255, читает и видит другое (D8).
  Любой шум полупрозрачных пикселей так обнаружим.
- **Снятие шума.** Любой шум, которому безразличен повтор, сохраняет то, по чему он решает. Трекер, знающий
  схему, может хэшировать это и получить настоящий отпечаток: у нынешнего — `v & 0xfe` (200 зёрен дают 1 хэш), у
  (q) — `alpha >> 1`. Защита — только от точного сравнения хэшей. Так было и раньше.

## Цена

- **Код.** `fingerprint.js`: заменить `fpNoisePixels` и добавить две функции, около 15 строк; перехваты и `copyOf`
  не меняются. То же в `fp_patch.js`, чтобы стенд мерил то, что в продукте. Пересобрать `page-shim.js`
  (`ios/scripts/build-shim.py`). Во время выполнения дополнительной работы нет.
- **Хэши.** Хэш канваса каждой сессии сменится один раз, при обновлении. Приложение ещё не выпущено, так что
  сейчас это ничего не стоит; после выпуска это была бы «смена устройства» для каждого аккаунта.
- **CI приложения.** Красный — нынешний шум:
  - ошибка `canvasNoiseLowBit` в `Faults.swift`; шим за этим флагом держит старую функцию, около 10 строк;
  - в `/env` тестового стенда строка `png:` — то же, что `dataURLvsImageData` в q2;
  - в `SettingsTests` `png: 0` при включённом шуме;
  - строка в `faults.tsv`.

  На рисунке размера пробника старый шум даёт не меньше 9 байт (минимум по 500 зёрнам) [смоделировано].
- **Стенд q2.** `q2.M.dataURL-vs-imageData` из LEAK становится PASS. Добавить:
  - D2 — разбор PNG в странице: `DecompressionStream('deflate')` и снятие фильтров, около 35 строк;
  - D4 и D6;
  - D10 — чёрный текст;
  - **в неподменённой сессии N — таблицу всех 65 536 пар (значение, альфа)**: родные put/get должны совпасть с
    формулами, на симуляторе и на iPhone. Это единственная страховка от зависимости от формул. Если какая-то iOS
    её не пройдёт, запасной путь — калибровка: один родной put/get таблицы 256×256 на окно (около 8 строк) и
    таблица вместо формул.
- **Объём.** Около 15 строк в шиме, около 10 — на красный, около 60 — в проверках стенда, плюс один прогон q2 на
  iPhone, который можно сделать в следующий заход владельца. Перенос из Chromium на модель показал
  чувствительность: те же формулы внутри Chromium, где округление расходится в 1,5% случаев, дают 3 байта
  расхождения. Поэтому проверка таблицы на устройстве обязательна.

## Другие выдачи в нынешнем шиме (касаются и приложения)

1. **Подпрямоугольник не сходится с полным чтением** [замерено]: 95–110 байт; копия со сдвигом — около 280.
   Причина: шум привязан к месту пикселя внутри возвращённого ImageData (`i >> 2`). (q) это исправляет.
2. **Чёрный и белый текст перестаёт быть чёрным и белым** [замерено]: 321–395 байт. (q) исправляет.
3. **`copyOf` берёт функции, которые страница может подменить, в момент вызова** [прочитано в коде, не
   запускалось]: `createElement`, `getContext`, `drawImage`, `putImageData`, ширину и высоту. Страница, обернувшая
   `putImageData`, увидит при `toDataURL` вызов, которого у родного WebKit нет. Исправление: взять их при установке
   шима и вызывать через `Reflect.apply`, около 10 строк.
4. **Цветовые пространства и WebGL** [прочитано в коде, не запускалось]:
   - копия в `copyOf` — sRGB, и `display-p3`-канвас при `toDataURL` пересчитывается;
   - у WebGL-канваса PNG шумится 2D-шумом, а `readPixels` — `fpNoiseGL`, и они расходятся;
   - `getImageData(…, {pixelFormat: 'rgba-float16'})` в WebKit есть, а битовые операции испортят
     Float16Array. Нужна проверка `data instanceof Uint8ClampedArray`; включён ли этот формат на iOS 27, не
     проверено.
