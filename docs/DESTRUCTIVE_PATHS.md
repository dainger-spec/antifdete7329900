# Разрушительные пути: восемь вопросов, которые ждут ответа

Состояние на 1 ноября 2026, вершина ветки `claude/secret-partner-setup-e505tc` — `154b8f6`.

Аудит всех мест, где Lumen удаляет, перезаписывает или усекает данные пользователя, сделан 1 ноября
на коммите `2da93c9` и отправлен владельцу письмом. Здесь собраны:
- вопросы из него, которые ждут ответа, заново проверенные на `154b8f6`;
- полный список мест, обновлённый под текущий код (приложение А);
- тесты, которыми риски воспроизводятся (приложение Б).

Полная проверка — пункт 6 плана от 1 ноября — остаётся в плане, и этот документ её основа.

**Как проверено.** Для R1, R1b, R2, R3, R4 и R7 есть тесты-воспроизведения. Каждый утверждает
безопасное поведение и сейчас падает, а это значит, что риск есть. На `154b8f6` упали все шесть. R8 и
вопрос 8 проверены по коду.

**Общая причина.** Охранник перезаписи `DocumentFormat.guardOverwrite` запрещает писать только поверх
файла более новой версии. Файл, который не открылся, он пропускает. Безопасность зависит от того, кто
пишет: прочитал ли он файл с ошибкой (`try`) или подставил пустое значение (`try?`, `?? Default()`).
«Не открылся» сегодня значит одно из двух: файл повреждён или он из другого хранилища или профиля.
Смена пароля ключей не меняет, поэтому файлы из копии, сделанной до смены, открываются.

## Вопросы

### 1. R1 — `config.bin` перезаписывается через редактор профиля (главный)

- **Что перезаписывается.** `config.bin` профиля: все его настройки, включая прокси.
- **При каком состоянии.** `config.bin` не читается. Редактор всё равно открывается: показывает ошибку и
  пустую форму, а кнопка «Сохранить» доступна. `AppModel.updateProfile` читает настройки через `try?`,
  получает пустоту и записывает настройки по умолчанию с правками формы поверх нечитаемого файла. Пишет
  он это ещё до проверки имени, так что даже ошибка имени запись не останавливает.
- **Чем грозит.** Если человек не впишет прокси заново, профиль получает настройки по умолчанию без
  своего прокси, и следующий запуск идёт напрямую, с настоящим адресом. Случай редкий (порча файла), но
  из восьми у него худшее последствие — работа без прокси. Поэтому он первый.
- **Проверено.** Тест R1 падает: 200 байт нечитаемого файла заменены 344 байтами новых настроек.
- **Предложение — да.**
  - Нечитаемый `config.bin` не перезаписывается нигде. Запись проверяет, что существующий файл
    открывается ключом профиля, а иначе отказывает.
  - Редактор при ошибке чтения не даёт сохранить и говорит почему.
  - Профиль остаётся незапускаемым, пока не вернут читаемый файл из копии или не удалят профиль.
  - Вариант «отложить файл и записать настройки по умолчанию» не предлагаю: профиль остался бы без
    прокси.
  - Сделать первым из восьми, отдельным коммитом (это сетевой путь), не дожидаясь полной проверки.

### 2. R1b — прогрев: план `warmup.bin` и расписание `warmup-schedule.bin`

- **Что перезаписывается.** Адреса плана прогрева, введённые человеком, и настройки повтора.
- **При каком состоянии.** Файл не читается.
  - План: `AppModel.warmUpPlan` молча отдаёт пустой план, и экран прогрева показывает его без единого
    слова. Любое сохранение («Повторять», запуск) пишет поверх.
  - Расписание: координатор пишет в журнал и считает, что расписания нет. Включение повтора записывает
    новое поверх.
- **Чем грозит.** Пропадают введённые адреса и пара чисел. Риск низкий.
- **Проверено.** Тест R1b падает: 120 байт нечитаемого файла заменены 151 байтом.
- **Предложение — да.** Нечитаемый план или расписание откладывается в `*.unreadable`, как это уже
  сделано для `settings.bin` (2aaba12). Экран прогрева говорит, что сохранённый план не прочитан.

### 3. R2 — синхронизация отправляет старый `config.bin`, возвращённый из копии, поверх новых настроек

- **Что перезаписывается.** Настройки профиля на сервере и на всех устройствах. Новых настроек не
  остаётся нигде.
- **При каком состоянии.** Человек вернул из резервной копии старый `config.bin`, а `sync-state.bin` у
  него текущий. Файл выглядит «изменённым здесь», сервер — «не менялся», и синхронизация отправляет
  старые настройки поверх новых. Другие устройства их забирают. Копии нет: конфликта при этом не
  возникает.
- **Чем грозит.** Незаметный откат настроек на всех устройствах, в том числе прокси: старый прокси
  вместо нового.
- **Проверено.** Тест R2 падает.
- **Предложение — да.**
  - Если только что «изменённый здесь» `config.bin` старше серверной копии (по `settingsModifiedAt`),
    это не правка, а возврат из копии.
  - Такой файл не отправляется поверх. Остаётся серверная версия, а возвращённая сохраняется копией при
    конфликте и показывается.
  - Часы здесь решают только, какая версия станет действующей. Ни одна не отбрасывается — то же
    правило, что для паролей.
  - Минус: если человек намеренно вернул старые настройки, они придут копией и не применятся сразу.

### 4. R3 — папка удалённого профиля, возвращённая из копии, удаляется снова

- **Что удаляется.** Папка профиля со всеми его данными.
- **При каком состоянии.** Профиль удалён (в индексе есть запись об удалении), а его папку вернули из
  резервной копии.
  - При следующей разблокировке уборка удаляет папку снова: запись об удалении сильнее.
  - Если вернуть папку вместе со старым `index.bin`, профиль снова виден, но следующая синхронизация
    удаляет его опять: запись об удалении приходит с сервера.
- **Что изменилось с аудита.** С 383ad82 в папке профиля лежит копия его ключа (`key.bin`), поэтому
  возвращённая папка расшифровывается и без старого индекса. Профиль, который индекс записал удалённым,
  из копий ключа в список не возвращается — так задумано, — и уборка его удаляет.
- **Чем грозит.** Восстановить удалённый профиль из резервной копии сейчас нельзя.
- **Проверено.** Тест R3 падает.
- **Вопрос — решение за вами.** Поддерживать ли восстановление удалённых профилей из копии?
  - Если да: найденная при разблокировке папка удалённого профиля не удаляется, а показывается
    («папка удалённого профиля вернулась»), и её можно вернуть. Запись об удалении снимается, и это
    расходится синхронизацией. Старый индекс благодаря копии ключа не нужен.
  - Это меняет модель удаления в синхронизации: возвращение должно побеждать удаление на других
    устройствах. Значит, это отдельная работа и ваше решение о модели данных.
  - Если нет: оставить как есть и написать об этом в документации.
  - Я за «да», отдельной работой.

### 5. R4 — вторая копия при конфликте настроек перезаписывает первую

- **Что перезаписывается.** `config.bin.conflict` — проигравшая версия настроек первого конфликта.
- **При каком состоянии.** Настройки одного профиля дважды изменили на двух устройствах между
  синхронизациями. Каждый конфликт оставляет проигравшую версию в одном и том же файле.
- **Чем грозит.** Проигравшая версия первого конфликта теряется. Кроме того, копию человек нигде в
  интерфейсе не видит: есть только счётчик конфликтов в статусе синхронизации.
- **Проверено.** Тест R4 падает: после двух конфликтов осталась одна копия.
- **Предложение — да, уточнено.**
  - Каждая копия хранится отдельно (`config.bin.conflict`, `-2`, `-3`…), с устройством и временем,
    как у паролей (e10d91f).
  - Копии видны в редакторе профиля с кнопкой «Использовать эту версию».
  - В аудите я предлагал предел в пять копий. Уточняю: без тихого удаления. Если копий больше пяти,
    профиль просит разобрать их, а не удаляет старые сам.

### 6. R7 — миграция из песочницы удаляет папку назначения без повторной проверки

- **Что удаляется.** Папка назначения (хранилище вне песочницы) со всем, что в ней оказалось.
- **При каком состоянии.** Первый запуск сборки без песочницы. `UnsandboxedMigration.plan()` проверяет,
  что папка назначения пуста, а `perform()` удаляет назначение, если оно существует, и ещё раз не
  проверяет. Если между двумя вызовами там что-то появилось, это удаляется.
- **Чем грозит.** Гонка теоретическая: миграция идёт при запуске раньше всего остального. Но удаление
  держится не на проверке в момент удаления.
- **Проверено.** Тест R7 падает.
- **Предложение — да.** `perform` удаляет назначение, только если в этот момент это пустая папка. Иначе
  миграция останавливается, ничего не трогает и говорит об этом.

### 7. R8 — частичный открытый текст профиля после падения во время разворачивания архива

Это не удаление, а приватность: остаётся то, что должно было исчезнуть.
- **Что остаётся.** Архив данных сайтов (`webdata.pbsa`) или дома Safari (`safarihome.pbsa`)
  разворачивается во временные скрытые каталоги `.<имя>.unseal-<uuid>`. Ошибку внутри процесса
  разворот убирает сам. Но если процесс падает или его убивают посреди разворота, в каталоге остаётся
  часть открытого текста профиля.
- **При каком состоянии.** Падение или принудительное завершение процесса во время запуска профиля или
  разблокировки.
- **Чем грозит.** Открытый текст профиля на диске, вне хранилища. Его не убирает ни запуск, ни
  разблокировка, ни уборка. Из Time Machine такие каталоги исключены, но на диске они лежат.
- **Проверено по коду.** Каталог создаётся в одном месте (`EncryptedDirectoryArchive.unseal`), а уборки
  оставшихся нет нигде.
- **Предложение — да.** Удалять оставшиеся `.…unseal-…` при запуске профиля (перед разворотом его
  архивов) и при разблокировке. Они нигде не используются: законченный разворот переносит каталог на
  место.

### 8. `cookies-import.bin` — нечитаемая очередь импорта cookies удаляется

- **Что удаляется.** Очередь cookies, импортированных из файла и ждущих запуска профиля.
- **При каком состоянии.** Очередь не читается при запуске. Очередь, записанную более новой версией,
  это не касается — её не трогают. Запуск пишет в журнал, удаляет очередь и показывает человеку
  сообщение.
- **Чем грозит.** Потеря небольшая: это временная копия cookies из файла, который человек выбрал сам.
  Файл остаётся у него, импорт можно повторить.
- **Проверено по коду** (`ProfileManager.applyQueuedCookies`, `ProfileRepository.clearImportedCookies`).
- **Предложение — нет, оставить как есть.** Отложить очередь в сторону можно, как `settings.bin`, но
  ценности в ней нет, а лишний файл с cookies в папке профиля ни к чему.

## Что изменилось с аудита (`2da93c9` → `154b8f6`)

- **R6 снят с повестки.** Он касался `keycheck.bin` из смены ключей, а смена ключей отложена владельцем
  отдельным проектом (ветка `rekey-parked`, не отправлена). На ветке такого файла нет.
- **Устарели строки аудита про код отложенной смены ключей.** Это `staleHeader`, `keycheck.bin`,
  `rekey.json` и файлы «под другим ключом». Без смены ключей смена пароля ключи не меняет, поэтому:
  - файлы из копии, сделанной до смены, открываются;
  - старая копия `vault.json` открывает хранилище старым паролем. Это ограничение описано в
    `ARCHITECTURE.md` и закреплено тестом.
- **R3** — копия ключа в папке профиля (383ad82), см. вопрос 4.
- **Исправлено после аудита, проверено CI:**
  - хранилище cookies, поднявшееся пустым, не записывает удаление всех cookies (2d0d237);
  - остатки неполного удаления при запечатке выбрасываются по маркеру (6762359);
  - пароли при конфликтах хранят все версии, ни одна не пишется поверх другой (8c77029, e10d91f);
  - потерянный индекс собирается из копий ключа (383ad82);
  - заголовок хранилища на сервере (496f634).
- **Новые пути записи и удаления из этих коммитов проверены тем же правилом «нечитаемое — не пустое».
  Новых рисков нет:**
  - `passwords.bin.conflict` удаляется, только когда файл, прочитанный заново, содержит всё из него, а
    нечитаемая копия остаётся;
  - `key.bin` переписывается только из прочитанного индекса;
  - заголовок на сервере пишется только поверх более старого;
  - маркеры запечатки появляются после записи архива и до удаления.
- **На стороне синхронизации удалений нет вообще.** У транспорта три операции: перечислить, прочитать
  и записать с проверкой ревизии. Потеря на сервере возможна только записью поверх, и R2 — единственный
  найденный такой путь без слияния.

| `history.bin`, `bookmarks.bin` | Посещения, закладки | Нет | Нечитаемый файл останавливает запуск профиля раньше, чем создаются хранилища истории и закладок. |
| `history.bin`: сокращение по сроку | Политика хранения из настроек профиля | Нет | Без читаемых настроек нет запуска; синхронизация при нечитаемых настройках историю не режет (93d27ce). |
| `cookies.bin`, `cookies-baseline.bin` при синхронизации cookies | Запуск и остановка профиля | Нет | Нечитаемый файл — сообщение, ничего не сохраняется. Хранилище, поднявшееся пустым, не записывает «всё удалено» (2d0d237). |
| `cookies.bin` при **выключенной** синхронизации cookies | Каждый запуск профиля и выключение в настройках | Да, по замыслу | Допустимо. Файл — только перевозка cookies между устройствами; cookies профиля живут в `webdata.pbsa`. В пустом документе нет записей об удалении, и на других устройствах ничего не удаляется. |
| `cookies-import.bin` | Запуск профиля после импорта | Да, по замыслу | Вопрос 8. |
| `warmup.bin`, `warmup-schedule.bin` | Сохранение плана, включение повтора, прогон по расписанию | **Да — R1b** | Риск, низкий. |
| `tabs.bin` | Каждая остановка; удаляется, если «восстанавливать вкладки» выключено | Да, по замыслу | Допустимо: файл значит «вкладки последнего запуска». Но нечитаемый файл при запуске только пишется в журнал, а человеку ничего не говорится. |
| `webdata.pbsa`: запечатка | Остановка, разблокировка после падения, выход | Нет | Архив пишется только из каталогов WebKit, которые есть. Нечитаемый архив останавливает запуск до создания хранилища. Разворот идёт во временные каталоги и встаёт на место только после проверки до конца. Остатки неполного удаления выбрасываются по маркеру (6762359). |
| `safarihome.pbsa`: запечатка | Остановка, разблокировка после падения | Нет | То же. Дом без единого файла поверх архива не запечатывается (54812e7). |
| Каталоги WebKit и дом Safari после запечатки | Сразу после записи архива | — | Удаляются только после записи маркера. Без маркера ничего не удаляется: открытый текст запечатывается целиком при следующей разблокировке. |
| Временные каталоги разворота `.…unseal-…` | Разворот архива при запуске и разблокировке | — | **R8.** |
| Эфемерный профиль | Запуск и остановка | Безопасная сторона | Дом Safari и данные сайтов выбрасываются по настройке «эфемерный». Если настройки не читаются, профиль считается **не** эфемерным, и всё сохраняется. |
| `config.bin.conflict` | Конфликт настроек при синхронизации | Нет | **R4.** |

### А.3. Папки профилей

| Что | Когда срабатывает | «Не прочитал» | Вывод |
|---|---|---|---|
| Удаление профиля человеком | Подтверждённое действие | — | Сначала индекс (запись об удалении), потом папка, потом данные WebKit. |
| Уборка при разблокировке и после синхронизации | Только папки, которые **прочитанный** индекс записал удалёнными | Нет (78cecaa) | Безопасно: нечитаемый или отсутствующий индекс списка удалённых не даёт, и ничего не удаляется. Исключение — возвращённая папка удалённого профиля: **R3**. |
| Удаление через синхронизацию | Запись об удалении в индексе с сервера | Нет | Индекс с сервера расшифровывается мастер-ключом; если он не читается, синхронизация останавливается раньше любого удаления. Слияние индексов — объединение. |
| Откат папки при неудачном создании | Ошибка внутри `create` | — | Папку только что создал этот же вызов, в индекс она не попала. |
| Каталоги WebKit удалённого профиля | Удаление профиля здесь или через синхронизацию | — | Только по идентификатору удалённого профиля. |

### А.4. Вне хранилища

| Что | Когда срабатывает | Вывод |
|---|---|---|
| `SafariChromeHome` в папке хранилища | Один раз | Безопасно: открытый текст старого режима разработчика `--safari-chrome`, ни один профиль туда не писал. |
| Ключи в `~/Library/Preferences/com.apple.Safari.plist` | Один раз после разблокировки, вне песочницы | Безопасно: удаляется только ключ из нашего списка и только со значением, которое записали бы наши профили. |
| Миграция из песочницы | Первый запуск сборки вне песочницы без своего хранилища | Переносит, а не копирует; удаляет только пустую папку назначения, но проверяет это заранее: **R7**. |
| Обновления | Загрузка, установка, отказ | Удаляются только файлы в каталоге загрузки и временный каталог установки рядом с приложением. |
| Временные файлы записи | Любая запись | Удаляются только собственные временные файлы со скрытым именем, заменяемые атомарно. |

### А.5. Частичное восстановление из резервной копии

Что происходит, если вернуть из копии один файл или папку, а остальное оставить текущим.

| Вернули | Результат |
|---|---|
| `vault.json` из копии до смены пароля | Открывает хранилище старым паролем — все данные, в том числе записанные после смены: смена пароля перезаворачивает тот же ключ (ограничение, `ARCHITECTURE.md`). Ничего не удаляется. Синхронизация не отправит этот заголовок поверх более нового (496f634). |
| `index.bin`, старый | Профили, созданные после копии, возвращаются в список из своих копий ключа, с именами (383ad82). Удаляется только то, что старый индекс сам записал удалённым, — эти папки и так удалены. |
| `index.bin`, повреждённый | «Индекс не читается»: ничего не удаляется и не отправляется. |
| Папка удалённого профиля | Удаляется снова (**R3**). |
| Отдельный файл профиля | `passwords.bin`, `bookmarks.bin`, `history.bin`, `cookies.bin`: синхронизация сливает по записям, ничего не теряется. Записи об удалении на сервере не дают удалённому воскреснуть, а добавленное позже приходит с сервера. `config.bin` — **R2**: отправляется поверх новых настроек. |
| Повреждённый файл профиля | Запуск, окно паролей и синхронизация отказывают и ничего не перезаписывают. Исключения: `config.bin` через редактор (**R1**), `warmup.bin` и `warmup-schedule.bin` (**R1b**), `tabs.bin` (по замыслу), `cookies.bin` при выключенной синхронизации cookies (по замыслу), `cookies-import.bin` (удаляется с сообщением, вопрос 8). |
| `webdata.pbsa` или `safarihome.pbsa` | Если после падения остался незапечатанный открытый текст без маркера, он считается новее архива: запускается и запечатывается поверх восстановленного архива, и восстановление теряется. Если остатка нет, используется восстановленный архив. |
| `sync-state.bin`, старый | Всё считается изменённым с обеих сторон: слияние по записям, у `config.bin` — «новее, плюс копия». Ничего не теряется, с оговоркой R4. |

## Приложение Б. Тесты-воспроизведения

Каждый тест утверждает безопасное поведение, поэтому сейчас падает. Тест R6 убран вместе со сменой
ключей. Чтобы проверить на текущем коде, положите файл в `Tests/BrowserCoreTests/` и выполните
`swift test --filter DestructiveAuditRepro`. На `154b8f6` упали все шесть тестов. Когда риск закрыт,
его тест переходит в набор тестов ядра и должен проходить.

```swift
import XCTest
@testable import BrowserCore

/// Each test asserts the SAFE behaviour; a failure confirms the risk (docs/DESTRUCTIVE_PATHS.md).
final class DestructiveAuditRepro: XCTestCase {
    var root: URL!
    override func setUpWithError() throws {
        root = FileManager.default.temporaryDirectory.appendingPathComponent("pb-dest-\(UUID().uuidString)")
    }
    override func tearDownWithError() throws { try? FileManager.default.removeItem(at: root) }

    private func vault(_ name: String) throws -> ProfileRepository {
        try ProfileRepository.openedAtUnlock(vault: MasterVault.create(in: root.appendingPathComponent(name), password: "pw", iterations: 1_000))
    }

    // R1: a settings file that does not open is written over by a save (the editor's Save after a failed load).
    func testR1_UnreadableConfigIsNotWrittenOver() throws {
        let repository = try vault("v")
        let id = try repository.create(name: "P", configuration: ProfileConfiguration(timeZoneIdentifier: "Asia/Tokyo")).id
        let url = repository.configURL(for: id)
        let damaged = Data(repeating: 7, count: 200)
        try damaged.write(to: url)
        let stored = try? repository.loadConfiguration(id)
        XCTAssertNil(stored)
        // AppModel.updateProfile: savingEdit(over: nil), then saveConfiguration.
        try? repository.saveConfiguration(ProfileConfiguration().savingEdit(over: stored), for: id)
        XCTAssertEqual(try Data(contentsOf: url), damaged, "R1: the unreadable config.bin was written over")
    }

    // R1b: the same for the warm-up plan (AppModel.warmUpPlan shows an unreadable plan as empty).
    func testR1b_UnreadableWarmUpPlanIsNotWrittenOver() throws {
        let repository = try vault("v")
        let id = try repository.create(name: "P", configuration: ProfileConfiguration()).id
        try repository.saveWarmUpPlan(WarmUpPlan(addresses: "https://a.example/"), for: id)
        let url = repository.warmUpPlanURL(for: id)
        let damaged = Data(repeating: 9, count: 120)
        try damaged.write(to: url)
        XCTAssertNil(try? repository.warmUpPlan(for: id))
        try? repository.saveWarmUpPlan(WarmUpPlan(addresses: "https://b.example/"), for: id)
        XCTAssertEqual(try Data(contentsOf: url), damaged, "R1b: the unreadable warmup.bin was written over")
    }

    // R2: an old config.bin put back (partial restore) is pushed by sync over newer settings, everywhere, with no copy.
    func testR2_RestoredOldConfigDoesNotSilentlyReplaceNewerSettings() async throws {
        let server = LocalDirectorySyncTransport(directory: root.appendingPathComponent("server"))
        let a = try vault("A")
        let id = try a.create(name: "P", configuration: ProfileConfiguration(timeZoneIdentifier: "Asia/Tokyo")).id
        _ = try await SyncEngine(repository: a, transport: server).sync()
        let backup = try Data(contentsOf: a.configURL(for: id))            // the copy in a backup
        var edited = try a.loadConfiguration(id)
        edited.timeZoneIdentifier = "Europe/Oslo"
        try a.saveConfiguration(edited.savingEdit(over: try a.loadConfiguration(id)), for: id)
        _ = try await SyncEngine(repository: a, transport: server).sync()  // the newer settings are there
        try backup.write(to: a.configURL(for: id))                          // partial restore
        _ = try await SyncEngine(repository: a, transport: server).sync()
        let b = try ProfileRepository.openedAtUnlock(vault: await SyncEngine.bootstrap(transport: server, root: root.appendingPathComponent("B"), password: "pw"))
        _ = try await SyncEngine(repository: b, transport: server).sync()
        let kept = FileManager.default.fileExists(atPath: a.configURL(for: id).path + ".conflict")
            || FileManager.default.fileExists(atPath: b.configURL(for: id).path + ".conflict")
        XCTAssertTrue(try b.loadConfiguration(id).timeZoneIdentifier == "Europe/Oslo" || kept,
                      "R2: the newer settings were replaced by the restored copy everywhere, and kept nowhere")
    }

    // R3: a deleted profile's folder put back from a backup is deleted again at the next unlock.
    func testR3_RestoredFolderOfADeletedProfileIsKept() throws {
        let folder = root.appendingPathComponent("v")
        let repository = try ProfileRepository.openedAtUnlock(vault: MasterVault.create(in: folder, password: "pw", iterations: 1_000))
        let id = try repository.create(name: "P", configuration: ProfileConfiguration()).id
        let copy = root.appendingPathComponent("copy")
        try FileManager.default.copyItem(at: repository.directory(for: id), to: copy)
        try repository.delete(id)
        try FileManager.default.copyItem(at: copy, to: repository.directory(for: id))   // put back
        _ = try ProfileRepository.openedAtUnlock(vault: MasterVault.unlock(in: folder, password: "pw"))
        XCTAssertTrue(FileManager.default.fileExists(atPath: repository.directory(for: id).path),
                      "R3: the folder put back was deleted again at the next unlock")
    }

    // R7: the migration removes whatever is at the destination when it runs, not only what plan() saw.
    func testR7_MigrationNeverRemovesANonEmptyDestination() throws {
        let container = root.appendingPathComponent("container/Library"), library = root.appendingPathComponent("home/Library")
        let containerVault = UnsandboxedMigration.vaultFolder(in: container)
        _ = try MasterVault.create(in: containerVault, password: "pw", iterations: 1_000)
        let moves = UnsandboxedMigration.plan(containerLibrary: container, library: library, bundleID: "x.y")
        XCTAssertFalse(moves.isEmpty)
        let local = UnsandboxedMigration.vaultFolder(in: library)
        try FileManager.default.createDirectory(at: local, withIntermediateDirectories: true)
        try Data("mine".utf8).write(to: local.appendingPathComponent("note.txt"))   // appears after plan()
        try? UnsandboxedMigration.perform(moves)
        XCTAssertTrue(FileManager.default.fileExists(atPath: local.appendingPathComponent("note.txt").path),
                      "R7: a file that appeared at the destination after plan() was deleted")
    }

    // R4: a second conflict over a profile's settings writes over the first conflict's copy.
    func testR4_ASecondConflictKeepsTheFirstConflictsCopy() async throws {
        let server = LocalDirectorySyncTransport(directory: root.appendingPathComponent("server"))
        let a = try vault("A")
        let id = try a.create(name: "P", configuration: ProfileConfiguration()).id
        _ = try await SyncEngine(repository: a, transport: server).sync()
        let b = try ProfileRepository.openedAtUnlock(vault: await SyncEngine.bootstrap(transport: server, root: root.appendingPathComponent("B"), password: "pw"))
        _ = try await SyncEngine(repository: b, transport: server).sync()
        func edit(_ repository: ProfileRepository, _ zone: String) throws {
            var c = try repository.loadConfiguration(id)
            c.timeZoneIdentifier = zone
            try repository.saveConfiguration(c.savingEdit(over: try repository.loadConfiguration(id)), for: id)
        }
        try edit(b, "Europe/Berlin"); try await Task.sleep(nanoseconds: 20_000_000); try edit(a, "Asia/Tokyo")
        _ = try await SyncEngine(repository: a, transport: server).sync()
        _ = try await SyncEngine(repository: b, transport: server).sync()        // conflict 1
        let conflict = URL(fileURLWithPath: b.configURL(for: id).path + ".conflict")
        let first = try Data(contentsOf: conflict)
        try edit(b, "Europe/Paris"); try await Task.sleep(nanoseconds: 20_000_000); try edit(a, "America/Chicago")
        _ = try await SyncEngine(repository: a, transport: server).sync()
        _ = try await SyncEngine(repository: b, transport: server).sync()        // conflict 2
        let copies = try FileManager.default.contentsOfDirectory(atPath: b.directory(for: id).path).filter { $0.contains("conflict") }
        let now = try Data(contentsOf: conflict)
        XCTAssertTrue(copies.count >= 2 || now == first, "R4: the first conflict's copy was written over by the second (\(copies))")
    }
}
```
