Earlier versions wrote the settings profiles give Safari's own services (AutoFill, Safari Suggestions, fraudulent website warnings and a few others) into the file ~/Library/Preferences/com.apple.Safari.plist. Safari itself does not read that file — it keeps its settings in its own container — so none of Safari's settings changed. This version takes those entries out of that file once, after the first unlock: only those that still hold the value an earlier version wrote; one changed since stays as it is, and nothing else in the file is touched.

Safari's window in each profile keeps its own layout now — the window's size and place, the sidebar and favorites bar, the start page's sections — in that profile's encrypted data, rather than in one file shared by every profile. After the update each profile opens once with Safari's default layout.

Sync can now go through your Lumen account: Settings → Sync → Lumen Account, offered while this Mac is signed in. Nothing to type — this Mac's own sign-in reaches the Lumen server, which keeps only what is encrypted on the Mac; Lumen for iPhone signed in to the same account connects to the same vault with your master password. When the server's copy is not the one this Mac last synced with — restored from a backup, or deleted on the account page — the next sync compares everything again and puts this Mac's data back, merging rather than overwriting; an object refused for the plan's space waits while the rest syncs.

Less work where it grew with use. A profile that has browsed a lot starts sooner: its website data is restored without the copying that grew with the number of cached files. Stopping a profile, and quitting with profiles open, encrypts its website data again only when it changed since it was last encrypted, instead of at every attempt. And the Profiles window does far less at each change when there are hundreds of profiles or a long proxy list — while the list is being checked, too.

A vault you already have can be brought to a Mac that has none — a new Mac, or one whose disk was erased. On the first launch's master-password screen choose "I already have a vault": from your Lumen account (this Mac is already signed in, so the account's vaults are listed by when each was made and last changed), from a sync folder, or from a server of your own (its address, token and the vault's ID, now shown under Settings → Sync). Type that vault's master password and its profiles come down with their settings, proxies, passwords, bookmarks, history and cookies; this Mac then goes on syncing that same vault. Nothing is changed where the vault is kept, and nothing on the Mac counts as a vault until all of it has arrived: a download that is interrupted is kept and continued, not begun again. Through the account this needs a paid plan running, as sync does; the screen says so, and says when a new device has to wait. A second Mac can join a vault the same way: changes travel when each Mac runs Sync Now, and one profile should not run on two Macs at once. To replace a vault a Mac already made with the synced one, lock the app and choose "Forgot password…" — that vault is moved aside, not deleted — and then "I already have a vault".

Settings can be searched by what a setting is called, not only by the name of its page: type "zoom", "Dock" or "quit" above the sections and the page that holds it is listed with the setting it found; Return opens it, and the row is marked. The command palette (⌘K) finds single settings the same way. The Settings window now opens on the page you last used.

The menu bar has the app's everyday commands: Lock Vault (⇧⌘L), Check for Updates… and Account… in the Lumen menu; Proxies… (⇧⌘P) and Sync Now in File. Lock from the menu, the keyboard or the palette asks first while profiles are running and lists what it stops, as Quit does (Settings → Startup → Confirm quitting); the Lock button in the Profiles window works as before. Settings → Keyboard Shortcuts and Help now list every one of these keys.

Unlock with Touch ID. Settings → Security → Unlock with Touch ID (off by default; on a Mac with Touch ID): the vault opens with your fingerprint in place of the master password. Turning it on asks for the master password once. The password is still asked after the Mac restarts, after 14 days without typing it, when Touch ID does not recognise you, and to change it or show saved passwords — do not forget it, Touch ID does not replace it. What changes: while it is on, the vault's key is kept on this Mac behind its Touch ID, readable by Lumen only after your fingerprint and never leaving this Mac, instead of being in memory alone; turning it off, changing the master password or the Mac's fingerprints removes it.

The Profiles list for many profiles: Tags… on a selection adds and removes tags for all the selected profiles at once, and a right click on a selected row acts on the whole selection; the list can be ordered by name or by the last launch (the ⋯ menu's Sort By, or a click on the Name or State title); the search also finds a profile by its proxy's address or its exit country; the sidebar's Proxy Not Working gathers the profiles whose proxy did not answer. An error at a launch, a stop or a deletion names its profile. In Proxies: a filter by state (working, not working, not checked, unused), columns that sort, and Replace in Profiles… for a proxy that stopped answering. Import reads rows copied from a table (tabs, spaces, ";" or "," between the parts), and Import Cookies reads exports wrapped in Base64.

Warm-up is a section of its own. The sidebar's Warm-up lists every profile by where it stands — running now with the site and the step, waiting, needing attention, never warmed, warmed and when — and keeps each profile's last 50 runs with a report: the sites, how each was reached, pages, time, cookies gained, and what went wrong. Templates are kinds of browsing (an ordinary day, news, shopping and nine more) resolved for the country each profile's proxy exits in — a German profile reads German news and shops — and can be mixed with lists of your own (paste or a file; lines that are not addresses are named). New warm-up is one sheet for one profile or a selection, with Light, Normal and Deep and a sample of what a profile of each country will visit. The robot reads a page for as long as it is, scrolls in bursts, prefers headlines to menus and footers, reaches part of the sites through the search engine, accepts the cookie banners of some twenty-five consent tools, and leaves at once — and names — a CAPTCHA page, a sign-in or payment page; three pages in a row that do not load end the run as "the proxy does not answer". The queue warms as many profiles at once as the Mac allows (or 1–8), can be paused, and reports failures in the section instead of an alert each. The Profiles list marks a warmed profile and gathers the unwarmed under Not Warmed Up.

Virtual machines cost this Mac less while nobody looks at them. A machine whose window is minimised, covered, on another desktop or behind a locked screen no longer asks macOS for the highest timer precision, which keeps its wake-ups from being gathered with the Mac's others; it still runs on as before, and nothing in it changes. And a new setting for each machine, Screen off while hidden (off unless you choose it, in the machine's settings under Device): once the window has been out of sight for half a minute, the machine's display goes to sleep as a Mac's does, so that neither its pages nor its virtual graphics draw for nobody, and it wakes a second or two after the window is seen again. While it sleeps, pages in the machine are hidden, as on a Mac whose display slept, which a site can notice. It is done only where the machine's screen lock is off, as Lumen's tools set it; otherwise the setting says why the display stayed on. Machines take the new tools (version 14) by themselves at their next start.

Virtual machines have HTTP/3 and WebRTC now, through their proxy. A machine's UDP — QUIC (HTTP/3), WebRTC and the like — goes through the proxy's own UDP relay where the proxy carries it: a SOCKS5 proxy with UDP (UDP ASSOCIATE), from the same address as its pages. Before each start Lumen checks that, as the Proxies section does — a STUN request through the proxy, never from this Mac directly — and turns UDP on for that run only if so; a site then sees the proxy's address in WebRTC, as in the pages. With an HTTP proxy, a proxy that does not carry UDP, one whose UDP leaves from another address, or when it cannot be told, HTTP/3 and WebRTC stay off and the machine's row says why; UDP never goes around the proxy. A machine without a proxy sends its UDP as this Mac's own, as it sends its pages — but not while this Mac's network settings name a proxy. DNS and the time are still answered inside Lumen, and nothing goes to a local network. A start with a SOCKS5 proxy can take a second or two longer for the check (up to nine seconds with a proxy that accepts UDP and carries nothing).

The welcome window — "welcome" written as with a pen — greets you at the first start of Lumen only. Whoever wants it every time turns on Settings → Appearance → Greet with the welcome window at every start (off by default).

WebRTC goes through a profile's connection by itself. New profiles get the WebRTC choice Automatic (Settings → New Profiles → WebRTC through the profile's connection automatically, on by default; turn it off to have new profiles start with WebRTC Disabled as before): with a SOCKS5 proxy WebRTC goes through the proxy, from its address, held there by Lumen's network guard; without a proxy it works as in Safari; with an HTTP proxy, which cannot carry UDP, it stays in the pages and connects nowhere. WebRTC never shows another address than the pages do. Existing profiles keep their choice — the profile's settings now offer Automatic too, and say under the choice what it comes to for that profile right now (its proxy's type, the network guard), with a link to set the guard up where only the guard is missing. If the guard is not set up, Settings → New Profiles says so with the same link.

WebRTC that must not connect is no longer simply taken out of the pages. Where WebRTC is Disabled or the proxy cannot carry it (HTTP, or a SOCKS5 proxy without UDP or whose UDP leaves from another address), it now stays in the pages as Safari has it — the same interfaces, codecs and capabilities, offers that look like Safari's — and connects nowhere: it gathers no address at all and sends nothing, as Safari does on a network that lets no UDP through. A missing WebRTC, and the "blocked" fingerprinting pages showed for it, was a mark no Safari has. This is done only where nothing can go around the connection even if a page got past Lumen's script: without a proxy, or with the network guard holding the profile to its proxy. Without the guard (and in a profile whose proxy has sites that bypass it) WebRTC is taken out of the pages as before.

The iPhone and iPad views are gone: a profile is Safari on this Mac. The profile settings no longer offer a view for websites, and with the views went the iPhone window (its bottom bar and tab overview) and the full iPhone disguise. A profile saved as an iPhone or iPad view — on this Mac, synced from another or imported from a .pbprofile file — opens as a Mac profile — Safari on this Mac, with this Mac's User-Agent — and keeps its other settings.

Virtual machines, sturdier where testers look first. A machine with a proxy whose proxy goes down while it runs, or stops taking its user name and password, now says so in its row and window — and, as before, nothing leaves it past the proxy; it connects again by itself once the proxy answers. The download of macOS says it is waiting for the network when nothing has come for a few seconds (Wi-Fi gone, a VPN reconnecting) instead of showing the last speed and time left, and goes on by itself; a download that stops says why — a full disk, the network, Apple's refusal — with what to do, and what was fetched is kept. An installation that fails or is cancelled no longer leaves its half-written system (up to 20 GB) on the disk, nor does a machine's first copy on a disk that is not APFS. Every failure of a machine, its setup or its helper is said in English or Russian with what to do, and the system's own words below as a technical detail — no bare error codes; Force Stop no longer reports that the machine "ended unexpectedly". Lumen running in a virtual machine itself says at once that machines need the Mac itself (macOS runs no virtual machine inside another). Two machines at once on a Mac with 8 GB of memory are said to take all of it (a warning, not a refusal). A vault on a disk that is not APFS is no longer refused the setup for want of room it has.

Lost cookies come back. While a profile runs, Lumen now keeps its last three snapshots of the profile's persistent cookies — taken every few minutes when they change and when the profile stops, encrypted with the profile's own data on this Mac and never synced. If a crash, a forced quit or a damaged cookie store loses them, the next launch puts back the cookies the store lacks before the first page loads, and the profile's window says "Cookies were restored from a snapshot of …". Cookies you or a site deleted stay deleted: a sign-out, a clear, a deletion through WebDriver or a cookie import is taken into the snapshots, and after a crash that left the cookie store whole, cookies are put back by themselves only when it kept fewer than half of them. Expired and session cookies are never brought back. With cookie sync on, a restored cookie never replaces a newer one from another device, and the loss is not sent to your other devices as deletions. Restore Cookies from a Snapshot… in a profile's menu lists the snapshots with their times and cookie counts and puts one back, after asking. The setting is in each profile's settings under Data (on by default; turning it off removes the snapshots); ephemeral profiles keep none.
