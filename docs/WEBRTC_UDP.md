# WebRTC и UDP в профилях с прокси: что измерено и какие есть пути

> **Решение 2 ноября 2026.** Пакетный туннель заменён: WebRTC профиля несёт ретранслятор (TURN на
> 127.0.0.1 в процессе Lumen) через UDP ASSOCIATE его прокси, а сетевая защита — фильтр содержимого,
> системное расширение без права открывать соединения — держит процессы такого профиля на его прокси.
> Устройство, решения и проверки — в [TUNNEL.md](TUNNEL.md); ниже — исследование, которое к этому привело.


Состояние на 1 ноября 2026. Подготовка к туннелю по поручению владельца от 1 ноября: измерения и
предложение, без кода в продукте. Измерения — на ветке `claude/measure-webrtc-udp` (не вливается),
CI-прогон 545, раннеры macOS 26.6.2 и macOS 27.0.1 (Safari тех же версий); инструменты — `scripts/measure/` на той же ветке.

Правило, которое не обсуждается: режима «пропустить мимо и надеяться» нет. Если UDP не может пройти
через прокси профиля, он не идёт никак, и пользователь об этом знает.

## Коротко

1. **Сегодня утечки нет — WebRTC в профиле с прокси просто нет.** С HTTP CONNECT и с SOCKS5 (с UDP у
   прокси и без, при «unrestricted» и по умолчанию) страница не видит `RTCPeerConnection`, и мимо прокси
   не уходит ни одного пакета — ни UDP, ни DNS, ни TCP. Измерено захватом пакетов на macOS 26 и 27.
   Через релей WebRTC идёт только там, где есть туннель; в нынешней сборке его нет, поэтому SOCKS5 сейчас
   ведёт себя так же, как HTTP: отказ, не утечка.
2. **Решающий вопрос — UDP у настоящих прокси — не измерен.** Ни одного прокси нашей аудитории у меня
   нет. Инструмент готов; нужен один запуск у вас. Заявления самих продавцов: UDP через SOCKS5 есть у
   меньшинства и обычно не включён по умолчанию.
3. **Развести UDP профилей по процессам можно, но не пакетным туннелем.** Измерено: UDP WebRTC
   отправляет процесс WebKit от имени процесса профиля, и два профиля различимы по процессу. Это даёт
   прозрачный прокси (`NETransparentProxyProvider`) или фильтр (`NEFilterDataProvider`); пакетный
   туннель процесс не различает.
4. **«UDP без снятия защиты и без второго приложения» достижимо только для прокси с UDP** и только
   системным расширением с одобрением администратора. Для остальных прокси честный ответ — UDP нет.
5. **Если измерение у вас подтвердит, что UDP есть у единиц, — вывод «пока не делать».** Оставить как
   сегодня и сказать прямо, а следующим шагом рассмотреть вариант 1 (раздел 5): он не даёт UDP, но
   убирает главный признак — отсутствующий `RTCPeerConnection`.

## 1. Что происходит с WebRTC в профиле сегодня (измерено трафиком)

**Как мерили.** Каждый сценарий — отдельный запуск приложения (`Lumen --capture-sites`, сборка без
песочницы) с одним профилем и двумя страницами:
- сбор кандидатов против двух публичных STUN-серверов (`stun.cloudflare.com`, `stun.l.google.com`);
- два соединения в одной странице, открывающие канал данных друг к другу.

Вокруг всех запусков — один захват пакетов всего Mac (`tcpdump -i pktap,all`): каждый пакет подписан
процессом, который его отправил, и процессом, от имени которого. Прокси работают на этом же Mac и
записывают каждую команду; петля (127.0.0.1) не захватывается. Поэтому пакет приложения или WebKit в
захвате (вне `lo0`) — это пакет, ушедший с Mac мимо прокси. Захвачено 2 936 строк (macOS 26) и 3 360
(macOS 27), у 98–99 % — с процессом.

| Сценарий | Что видит страница | Кандидаты | Прокси спросили | Пакеты приложения мимо прокси |
|---|---|---|---|---|
| без прокси, «unrestricted» (контроль) | `RTCPeerConnection` есть | srflx — **внешний адрес Mac** | — | 590–599: 6 STUN, 4 DNS, проверки связи; QUIC только на macOS 26 (49 пакетов); UDP шлёт WebKit от имени Lumen |
| HTTP CONNECT, «unrestricted» | `RTCPeerConnection` нет | нет | CONNECT 1 | **0** |
| HTTP CONNECT, по умолчанию | нет | нет | CONNECT 1 | **0** |
| SOCKS5 без UDP, «unrestricted» | нет | нет | CONNECT 1 | **0** |
| SOCKS5 с UDP, «unrestricted», без туннеля | нет | нет | CONNECT 1 (UDP ASSOCIATE не спрашивали) | **0** |
| SOCKS5 с UDP, по умолчанию | нет | нет | CONNECT 1 | **0** |
| SOCKS5 с UDP, через релей туннеля (обвязка) | есть | только relay | CONNECT 1, UDP ASSOCIATE 3, 30 датаграмм | **0**; канал данных открылся и доставил сообщение |

Одинаково на macOS 26 и 27 (кроме QUIC в контрольном сценарии).

**Ответы на вопрос 1.**
- **HTTP CONNECT: отказ, а не утечка.** Движок выключает WebRTC целиком: у страницы нет конструктора,
  нет кандидатов, наружу ничего. Выбор пользователя («unrestricted») на это не влияет.
- **SOCKS5 сегодня — то же самое.** Правило «через релей только при `.socks5`» верно, но срабатывает
  только при работающем туннеле. В нынешней сборке его нет, и SOCKS5 даже с UDP получает тот же отказ;
  UDP ASSOCIATE у прокси не спрашивается.
- **Через релей (код туннеля, запущенный без расширения):** страница видит только relay-кандидат, её
  UDP целиком идёт через UDP ASSOCIATE прокси, мимо — ноль пакетов.
- **Какой адрес видит страница.** Без WebRTC — никакой (по HTTP — адрес прокси). Через релей — адрес,
  с которого прокси выпускает UDP. На раннере он не совпал с адресом, который сайт видел по HTTP через
  тот же прокси: вероятно, сеть раннера выпускает TCP и UDP с разных адресов. У настоящих прокси бывает
  то же самое, и это отдельная проверка инструмента вопроса 2.
- **Контроль показывает, что ловушка работает.** Без прокси страница получила srflx-кандидат с
  настоящим внешним адресом Mac — ровно то, что было бы утечкой. Наружу ушли STUN, DNS к именам
  STUN-серверов, а на macOS 26 и QUIC. Захват такой трафик видит.

## 2. Поддерживают ли настоящие прокси UDP ASSOCIATE

**Измерено: 0 прокси нашей аудитории.** Проверить их из этой сессии нельзя:
- у меня нет ни одного такого прокси с логином;
- сеть облачного контейнера выпускает только HTTPS к разрешённым хостам;
- собственного сервиса прокси у Lumen пока нет (`ProxyOrigin.service` — заготовка).

Числа «сколько проверили, сколько ответили» появятся после одного запуска у вас.

Инструмент готов и проверен здесь на SOCKS5-сервере с UDP ASSOCIATE, без него и на мёртвом порту. Это
`scripts/measure/udp_associate_probe.py` на ветке измерения, только Python 3, ничего ставить не нужно.
Для каждого прокси он по шагам проверяет:
- вход по SOCKS5;
- адрес выхода TCP;
- ответ на UDP ASSOCIATE (0 — разрешено, 7 — «команда не поддерживается»);
- настоящий STUN-запрос через выданный UDP-порт к двум публичным серверам — сначала по имени (тогда имя
  разрешает прокси), потом по адресу;
- внешний адрес UDP и совпадает ли он с адресом TCP;
- одинаков ли порт для обоих серверов (endpoint-independent mapping). Без этого relay-порт работает не
  для каждого собеседника.

В отчёте прокси названы меткой и хешем, без адреса и логина.

```sh
git fetch origin claude/measure-webrtc-udp
git show origin/claude/measure-webrtc-udp:scripts/measure/udp_associate_probe.py > udp_associate_probe.py
# proxies.txt: по строке на прокси — socks5://логин:пароль@хост:порт # продавец, тип
python3 udp_associate_probe.py proxies.txt --json udp.json
```

Итоговая строка печатается так: «N прокси; TCP работает через …; UDP ASSOCIATE разрешён …; UDP
действительно проходит …; из них с тем же адресом, что TCP, …; с одинаковым портом …».

**Что говорят сами продавцы.** Это их заявления и обзоры, а не измерение; сайты из сессии открыть
нельзя, собрано поиском.

| Продавец | UDP через SOCKS5 | Как получить |
|---|---|---|
| Oxylabs (резидентные) | в бете | через менеджера аккаунта; страницы на разных языках противоречат друг другу |
| Evomi (резидентные) | есть | только корпоративным клиентам, включает поддержка вручную |
| Geonode (резидентные) | есть | флаг в логине, отдельный порт |
| IPRoyal | отдельный продукт «UDP proxy» | платно (по обзорам) |
| PapaProxy | есть | платная опция тарифа |
| Decodo (Smartproxy) | в одном обзоре «SOCKS5 with UDP» | документацией не подтверждено |
| Bright Data, SOAX, Webshare | не сказано | — |
| Proxy-Seller, Proxy6, 922 S5 | не сказано (SOCKS5 есть) | — |

Вывод из заявлений, не из измерений: у массовых продавцов UDP через SOCKS5 — редкость. Где он есть, он
чаще всего не включён по умолчанию: бета, корпоративный тариф, ручное включение, платная опция. Если
ваше измерение это подтвердит, путь «UDP через прокси профиля» работает для меньшинства прокси, и об
этом надо сказать прямо.

## 3. Что умеет NetworkExtension на macOS 26: отдельный путь UDP для каждого профиля

Вопрос: можно ли UDP одного процесса профиля завернуть в один туннель, а другого — в другой, на одной
машине одновременно.

**Измерено (основа для всего раздела).** UDP WebRTC отправляет процесс WebKit (в захвате имя обрезано до
`com.apple.WebKit`), но от имени процесса приложения: в метаданных пакета `eproc Lumen`. То же для DNS
к именам STUN-серверов: его делает `mDNSResponder` от имени Lumen. Два процесса приложения, запущенные
одновременно, дали два разных процесса WebKit, и каждый действовал от имени своего процесса Lumen:
- macOS 26: Lumen 13308 → WebKit 13312, Lumen 13309 → WebKit 13313;
- macOS 27: Lumen 14479 → WebKit 14480, Lumen 14477 → WebKit 14483.

В выпускаемой сборке каждый профиль — отдельный процесс, поэтому UDP профилей различим по процессу.
`eproc` в pktap — это то же сведение ядра о «действующем» процессе сокета, по которому NetworkExtension
приписывает поток приложению. Само расширение я не запускал, так что совпадение надо подтвердить на
железе.

**Пакетный туннель (`NEPacketTunnelProvider`) — по процессу нельзя.**
- Он получает IP-пакеты без сведений о процессе: метаданные пакета заполняются только в режиме per-app VPN.
- Per-app VPN выбирает трафик по приложению (`NEAppRule`: идентификатор подписи и designated
  requirement). Все процессы профилей — один и тот же Lumen с одной подписью, и правило их не различит.
- На машине одновременно работает один пакетный туннель. Туннель на каждый профиль невозможен. WireGuard,
  Tailscale и большинство VPN пользователя — тоже пакетные туннели, и включение нашего отключает их.
- Поэтому нынешний проект (`docs/TUNNEL.md`) различает профили не по процессу, а по адресу: у каждого
  профиля свой виртуальный TURN-адрес, и страница получает только его. Это работает без сведений о
  процессе, но держится на скрипте в странице (политика relay-only). Apple прямо пишет, что так
  использовать пакетный туннель не поддерживает (TN3120).

**Прозрачный прокси (`NETransparentProxyProvider`, с macOS 11) — по процессу можно.**
- Каждый поток, TCP или UDP, приходит с `sourceAppAuditToken` — токеном процесса, от имени которого он
  открыт. Из него получаются PID, путь и подпись; так советует Apple DTS.
- Поток можно отнести к профилю, а его UDP отправить через UDP ASSOCIATE именно его прокси. Это не
  «туннель на профиль», а решение на каждый поток: одно расширение ведёт разные профили через разные
  прокси одновременно.
- Это поддерживаемый Apple способ забирать часть трафика, и он уживается с VPN пользователя.
- Риски: разработчики сообщают о проблемах UDP в прозрачном прокси на macOS 15 и 26 — утечка mbuf и
  паника ядра при включённых правилах UDP (Apple завела FB14844573), «datagram too large» в
  `writeDatagrams`. Это форумы, а не документация, поэтому до решения нужна проверка на железе.

**Фильтр содержимого (`NEFilterDataProvider`) — по процессу можно, но только пропустить или
отбросить.** Перенаправить поток он не умеет. Зато годится как сетевой «аварийный выключатель» профиля:
всё, что его процессы шлют не на свой прокси (UDP и TCP), отбрасывается на уровне сети, а не скрипта в
странице.

**Что мешает проверить это здесь.** Системное расширение нельзя одобрить на раннере CI (нужна MDM), и
оно не грузится без подписи Developer ID с профилем. Поэтому ни нынешнее расширение, ни любое новое ещё
ни разу не запускалось. Первая возможность — подпись из задачи 1 и ручная проверка на вашем Mac.

## 4. Чем это отличается от конкурента

BlackBird, по их сайту, — «мультипрофильный браузер для iOS» с отдельными прокси у профилей. Их слова
про UDP в открытых источниках найти не удалось: поиск ничего не дал, а сайт из сессии не открывается.
Опираюсь на вашу цитату: их внутренний проксификатор UDP не поддерживает, и для UDP они просят
переключить WebRTC в Allow и включить внешний туннель (на iOS это приложение-VPN вроде Shadowrocket).

Что это значит на деле:
- WebRTC в режиме Allow без туннеля — прямая утечка настоящего адреса. Защита держится на том, что
  пользователь правильно включил второе приложение.
- Внешний туннель проводит UDP только туда, куда умеет его верхний прокси. Если у прокси нет UDP, UDP
  либо идёт напрямую (утечка), либо через другой сервер — а другой адрес у WebRTC и у HTTP тоже признак.

Наша цель — UDP без снятия защиты и без второго приложения. **Достижима, но только для прокси с UDP** и
ценой системного расширения (варианты 2–4 ниже). Для прокси без UDP никто — ни мы, ни BlackBird, ни
внешний туннель — не проведёт UDP через этот прокси: у него нет UDP. Наше отличие в этом случае — честный
отказ вместо утечки. Он уже есть и измерен (раздел 1).

## 5. Варианты и их честная цена

Все варианты, кроме нулевого, требуют системного расширения, подписанного Developer ID. Значит, сначала
должна пройти задача 1 (цепочка подписи). Скрипт задачи 1 заодно покажет, какие типы сетевых расширений
разрешают ваши профили: пакетный туннель, прозрачный прокси, фильтр.

**Вариант 0 — не делать.** Оставить как сегодня и сказать прямо.
- Есть: WebRTC в профиле с прокси выключен в движке, ничего не уходит мимо прокси (измерено). Работает
  с любыми прокси, без расширений и одобрений, работы — ноль. Надпись «WebRTC выключен» в профиле и в
  «Что видят сайты» уже есть.
- Теряем, если WebRTC в профилях просто не работает:
  - всё, что держится на WebRTC: звонки и видео в браузере (Google Meet, Zoom в браузере, голос Discord,
    звонки в веб-версиях мессенджеров), P2P-передачу файлов, часть игр, трансляций и удалённого доступа.
    Сайт либо скажет «браузер не поддерживается», либо функция молча не сработает;
  - неотличимость: в настоящей Safari по умолчанию `RTCPeerConnection` есть, и его отсутствие — признак,
    по которому профиль отделяется от обычных пользователей Safari. Это не утечка адреса, но это
    отпечаток;
  - сравнение «адрес WebRTC — адрес HTTP», которое делают антифрод-скрипты, становится невозможным;
    часть из них сочтёт это сокрытием.

**Вариант 1 — API есть, UDP нет (сетевой выключатель).** WebRTC в движке включён, а фильтр содержимого
отбрасывает всё, что процессы профиля шлют не на свой прокси.
- Страница видит `RTCPeerConnection` и собирает кандидаты, но ни один не уходит в сеть, соединения не
  устанавливаются — как в сети, где UDP закрыт. Работает с любыми прокси.
- Плюс сверх WebRTC: гарантия «ничего мимо прокси» на уровне сети для всех соединений процессов профиля,
  а не только для WebRTC.
- Цена:
  - системное расширение: одобрение администратором и отдельное разрешение фильтра;
  - право `content-filter-provider-systemextension` в профиле;
  - на CI не проверить;
  - функции WebRTC по-прежнему не работают;
  - «сеть без UDP при прокси» — тоже признак, хотя и обычный для корпоративных сетей;
  - если фильтр выключен или не одобрен, WebRTC обязан оставаться выключенным, как сегодня. Режим
    проверяется при каждом запуске профиля, а не один раз.

**Вариант 2 — то, что уже спроектировано: пакетный туннель и TURN-релей на профиль.**
- Только прокси с UDP. Страница видит только relay-кандидат, канал данных работает (измерено через
  обвязку, раздел 1).
- Цена:
  - системное расширение и два одобрения;
  - один пакетный VPN на машину: наш выключает VPN пользователя, и наоборот;
  - Apple такое использование не поддерживает (TN3120);
  - защита держится на скрипте в странице: если его обойти, настоящий адрес утечёт. Без варианта 1
    сетевой подстраховки нет;
  - «только relay» отличимо от обычной Safari: нет ни srflx, ни host-кандидатов;
  - код написан и проверен в CI с обвязкой, само расширение ни разу не запускалось.

**Вариант 3 — прозрачный прокси по процессу.** `NETransparentProxyProvider` забирает UDP-потоки
процессов профиля (по токену процесса) и шлёт их через UDP ASSOCIATE прокси профиля. Поток, который
провести нельзя, закрывается.
- Только прокси с UDP. Страница видит обычные кандидаты (srflx — адрес выхода UDP прокси): это ближе
  всего к Safari за этим прокси.
- Не нужны ни TURN, ни скрипт в странице. Уживается с VPN пользователя. Поддерживаемый Apple способ.
  Его основа измерена: процессы профилей различимы (раздел 3).
- Цена:
  - новое системное расширение (тип app-proxy, то же одобрение);
  - заметный объём нового кода;
  - известные проблемы UDP в прозрачном прокси на macOS 15/26 (сообщения о паниках ядра) — до решения
    проверить на железе;
  - на CI не проверить;
  - у прокси, чей UDP выходит не с того адреса, что TCP, страница увидит два разных адреса.

**Вариант 4 — 3 и 1 вместе.** Одно расширение и одно одобрение: прозрачный прокси для прокси с UDP и
фильтр для остальных.
- `RTCPeerConnection` есть во всех профилях. UDP идёт через прокси, где он есть, и не идёт нигде больше.
- Самый полный и самый дорогой вариант.

**Отклонено.**
- «UDP через наш сервер» (TURN на нашем сервере через TCP прокси): адрес WebRTC будет нашим, а не
  прокси. Это нарушает «только через прокси профиля» и само по себе признак.
- «Пропустить мимо»: запрещено правилом.

**Предложение.**
1. Сначала два ваших запуска: вопрос 2 (инструмент выше) и задача 1 (подпись).
2. Если UDP у ваших прокси — у единиц: вариант 0 сейчас, честно описанный, и вариант 1 следующим шагом.
   Он помогает всем профилям с прокси.
3. Если UDP у заметной доли: вариант 3 (или 4) вместо 2 — поддерживаемый API, нет конфликта с VPN, нет
   скрипта в странице, обычные кандидаты. Но только после проверки стабильности UDP на macOS 26 и 27 на
   железе.

## 6. Что нужно от владельца

1. Список прокси, которые реально продаются нашей аудитории (лучше по 5–10 у каждого продавца), и один
   запуск `udp_associate_probe.py`. Прислать итоговую строку и `udp.json`.
2. Запуск проверки подписи (задача 1): `python3 scripts/signing_check.py --profiles-only`, затем полный.
   Прислать `build/signing-check/report.txt`.
3. После этого — выбор варианта. До него код туннеля не пишется.
